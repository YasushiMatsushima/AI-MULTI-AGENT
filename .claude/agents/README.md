# カスタムエージェント運用ガイド

このディレクトリ配下のエージェントは、**コードの品質サイクル（レビュー → 修正 → テスト → ドキュメント）** を分業して担当します。本ドキュメントは各エージェントの役割と、組み合わせて使う際の標準ワークフローをまとめます。

## 構成ファイル

| ファイル | 役割 |
|---|---|
| [_shared.md](_shared.md) | 全エージェント共通のプロジェクトコンテキスト |
| [python-code-reviewer.md](python-code-reviewer.md) | コードレビュー専門（**読み取り専用**、コード変更不可） |
| [test-engineer.md](test-engineer.md) | テストの作成・実行 |
| [doc-writer.md](doc-writer.md) | docstring・README 等のドキュメント作成 |

## 各エージェントの責任境界

| 観点 | python-code-reviewer | test-engineer | doc-writer | メインClaude |
|---|---|---|---|---|
| コード読解 | ✓ | ✓ | ✓ | ✓ |
| バグ指摘 | ✓ | (Red 検出経由) | (乖離検出経由) | – |
| **コード修正** | ✗（物理的に不可） | ✗ | ✗ | ✓ |
| テスト作成 | – | ✓ | – | – |
| ドキュメント | – | – | ✓ | – |

**コード修正は常にメイン Claude（またはユーザー）の責務**。サブエージェントは検出・提案までを担当します。

## 標準ワークフロー

```
┌──────────────────────┐
│  ユーザー要求         │
└──────────┬───────────┘
           ↓
    ┌──────────────┐
    │ メイン Claude │
    └──┬───────────┘
       ↓ ①レビュー依頼
    ┌─────────────────────────┐
    │  python-code-reviewer    │ → バグ・セキュリティ・パフォーマンス指摘
    └──┬──────────────────────┘    + 🔁 下流への申し送り
       ↓ ②レビュー結果を受領
    ┌──────────────┐
    │ メイン Claude │ → コード修正を実施（または別タスクとして起票）
    └──┬───────────┘
       ↓ ③テスト依頼（修正後のあるべき動作を明示）
    ┌─────────────────────────┐
    │      test-engineer       │ → tests/ にテスト作成・実行
    └──┬──────────────────────┘    Green なら次へ
       │                            Red なら ⚠️ハンドオフフォーマット
       │                            でコード修正の必要性を報告
       ↓ ④全 Green を確認
    ┌─────────────────────────┐
    │       doc-writer         │ → tests/ を読んで仕様を docstring 化
    └─────────────────────────┘
```

## ハンドオフ仕様（重要）

### code-reviewer → test-engineer
レビュー出力の「🔁 下流エージェントへの引き継ぎ」セクションに、テスト作成時の禁止事項（特性化テスト禁止など）を明記する。

### test-engineer → メイン Claude（Red ハンドオフ）
テストが失敗してコード修正が必要なとき、以下のフォーマットで報告：

```
## ⚠️ コード修正が必要です（Red ハンドオフ）

### 失敗テスト一覧
| # | テスト名 | 対象ファイル:行 | 期待される動作 | 実際の動作 |

### 推奨修正方針
1. ファイル:行 — 修正内容
```

詳細は [test-engineer.md](test-engineer.md) の出力フォーマットセクション。

### doc-writer → メイン Claude（仕様乖離検出）
docstring 作成中に「テストが期待する動作」と「コードの実際の動作」に乖離があれば、ドキュメント化を一時停止してユーザーに報告する。

## アンチパターン（過去事例）

### ❌ test-engineer が code-reviewer の指摘を「現状追認テスト」にしてしまう
- 症状: バグだらけのコードに対し全テストが Green になる
- 原因: `pytest.raises(ZeroDivisionError)` のような特性化テストを書いてしまう
- 対策: [test-engineer.md](test-engineer.md) の「最重要原則」セクションで明示的に禁止

### ❌ doc-writer がコードのバグを「仕様」として記述してしまう
- 症状: `Raises: ZeroDivisionError` のような偶発例外が docstring に記載される
- 対策: [doc-writer.md](doc-writer.md) の「既知バグを仕様として記述しない」「仕様はテストから読み取る」セクション

### ❌ コードレビューが下流に何も申し送らない
- 症状: テスト担当が指摘事項の意図を取り違える
- 対策: [python-code-reviewer.md](python-code-reviewer.md) の「🔁 下流エージェントへの引き継ぎ」セクション

## 各エージェント呼び出しのタイミング目安

| ユーザー発話の例 | 起動すべきエージェント |
|---|---|
| 「このコードをレビューして」 | python-code-reviewer |
| 「テストを書いて」「テストを実行して」 | test-engineer |
| 「ドキュメントを書いて」「docstring を追加して」 | doc-writer |
| 「レビューしてテストも書いて修正もして」 | reviewer → メインで修正 → test-engineer の順で連鎖 |

## エージェントを変更したら
- 共通の前提を変更した場合は [_shared.md](_shared.md) を更新する（個別ファイルではなく）
- ハンドオフ仕様を変えた場合は本 README とエージェント両方を更新する
- 過去の事故事例は「アンチパターン」セクションに蓄積する
